# Native parameter binding extension — isolation and attribution

Version: NATIVE-PARAMETER-CONNECTION-TEST_ONLY-1. Explicit BindingCore only.
No edits to frozen TC, NBO, ContentEngine, FormalL0, catalog or body implementations.
A two-line read-only foreign-mode guard in ACore rejects this new lifecycle before
lease/schema/session writes. This changes admission for the new TEST_ONLY state,
not default recursive computation or action generation. No real database is used.

ReceiptEncoder is isolated to BindingCore. It copies supplemental
`typedExecutionReceipts` input into the actual frame.nearby_data, without mapping
parameter names or interpreting actions. Original FrameEncoder is unchanged.
The supplemental input is an external **synthetic typed incidence premise**,
not proof of a real execution and not a complete raw receipt/command adapter.
A receipt can provide a projection of observed assignment facts; completeness
of a body command is outside this experiment. Execution identity/status labels
are supplied test facts, not inferred from world change or fabricated as real.

Ordinary NativeEngine admission supplies native identities and observed Units.
The new BindingEngine stores the current receipt batch in a replaced input
register, not an ever-growing second history. The ordinary integration hook
validates exact explicit references, registers recorded incidence, and performs
one exact intermediate-identity composition over the current edge snapshot.
Both endpoint types and native declared ranges are checked. Invalid batches
reject as a whole; no type-compatible pairing, value search or replacement.
The result is stored in the same DirectedConnection collection and consumed by
**the unchanged TC ordinary Pair constructor**, before expected/partial processing.
S0 and S1 share this interpretation; evidence/provenance is not read to execute.
This is not a separate consumer, graph runtime, command dictionary or output adapter.

## External versus internal

- Catalog: supplies native port/slot/domain identities and legality.
- Sensor: supplies exact scalar values and observation reference identities.
- Synthetic receipt: externally records slot→0 (the initial assignment's author
  is external). Fixture naming chooses an explicitly declared premise; it does
  not run in formation or map the final candidate to an action.
- Generic formation/composition mechanism: externally given typed law.
- Actual histories: 0→1 versus 0→2 form different scalar edges through frozen TC.
- Integration: composes exact shared endpoints into slot→1 versus slot→2,
  neither of which occurs in the input receipt. Both are candidates, not commands.
- Ordinary constructor: produces corresponding actual UnitRef/Pair operands.
- Future adoption/execution: NOT_ESTABLISHED and not attempted.

The numerical role of these candidates is purely structural. A world scalar's
change is not proof it is useful, causally correct or should be adopted as a future
parameter. Legal range checks are not behavioral authorship or usefulness checks.
All supported candidates remain; no first/latest/best/nearest/random choice.
No full expression is assembled and no historical command is copied for execution.

ObservedReference receipt incidence is checked and can be registered/reused as
an external assignment premise. This first composition law does **not** create
new slot/reference candidates by reference history; that extension is unproven.
No real receipt acquisition/conversion is validated here. No general parameter
formation, world causal law, autonomous goal, action/adoption authority, mainline
adoption, behavioral closure, L1 or universal generative dynamics is claimed.

Original shared Unit/content 64 and relation 96 capacities are unchanged.
Non-fitting formation/construction rejects without cleanup/pruning/fallback.
Mode/version/DB guards prevent default or frozen TC silently taking over the
new database. Same A/DB recovery loads authoritative Current State, not audit
history, original raw receipts or reconstructed answers.
